# Research Source Strategy

## Founder / Operator Problem Sources

### Reddit
Use for concrete pain points, process complaints, questions, workflow confusion, and recurring operational problems.

### X
Use for current discussions, fast-moving business observations, founder/operator complaints, and short problem statements that may reveal a larger process issue.

### LinkedIn Owned Engagement
Initially use authorized comments/replies on posts the operator owns or manages. These can reveal follow-up questions and professional objections after content is published.

## Evidence / Verification Sources

### Official documentation
Primary source for current product/API capabilities, permissions, limitations, and integration behavior.

### GitHub
Use for technical evidence, implementation patterns, SDKs, examples, issue reports, and repositories relevant to a proposed solution. GitHub is not treated as the main source of ordinary founder pain.

## Manual Input

The operator can manually add a business problem, customer question, observation, or content idea. Manual ideas still pass through diagnosis, evidence checks, platform fit, and approval.

## Evidence Hierarchy

1. Official product/API documentation
2. Official repository or vendor-maintained GitHub source
3. Strong technical/community evidence
4. Community discussion / anecdotal evidence
5. Unverified claim

The final teaching content should distinguish verified product capability from suggested workflow design.

## Clustering Rule

Similar source items should strengthen a shared Master Insight rather than automatically create duplicate topics.

Example source cluster:
- Reddit founder says staff forget follow-ups
- X founder says leads vanish after first call
- LinkedIn comment asks who owns the next sales action

Possible shared Master Insight:
`The real problem is not lead generation; follow-up depends on memory instead of visible ownership and next actions.`
